9. THE EXTENSION DOES NOT MOVE EFFICIENCY, ONLY THE MATCHING FRACTION (critic item 7)
------------------------------------------------------------------------------------------------
Measured in the COMPOSED context by aligning c1 (no -EX) and c3 (-EX on) index-by-index -- valid
because the pass creates and destroys no TC (tool: fn_extpurity.py):
  TCs compared 614,208 | INDEX MISALIGNMENTS 0 | TCs extended 18,637 (3.03%), each exactly +2 OT
  hits (37,274 total) | matched -> FAKE 116 | fake -> matched 27 | net fake numerator +89
  BREAK RATE 0.622% of extensions destroyed an existing sim match
ANSWER TO THE QUESTION THE CRITIC POSED: 100% of the extension's eff/fake movement is a
matching-FRACTION change on TCs that exist in BOTH runs. The pass finds ZERO tracks and loses
ZERO tracks. So the "-6 sims" that -EX appears to cost are dilution, not physics loss -- which
means the extension is CHEAPER than its offer stated, and that is what made room for the band
braid in the composition budget.
HONEST LIMIT: 0.622% is a STRICT LOWER BOUND on wrong extensions. A foreign 2-hit append on a
pure 10-hit TC leaves 10/12 = 0.833, still above the 0.75 matching threshold, and is invisible to
the harness. Part of the +0.10/+0.19/+0.05 nhitOT move therefore rests on hits of provenance the
harness cannot validate, and the only truth signal available (116 : 27) is unfavourable at the
margin. This reproduces SKEPTIC-3's independent measurement (0.628% at 18,632 extensions) almost
exactly, so composition does not degrade extension purity.

    PHYSICS: the band lower |eta| edge. RECON-0 measured that a 2-hit chain-chain overlap is a
      real duplicate 44-57% of the time at |eta| 1.5-2.5 but only 8% in the barrel, so the tight
      braid must not reach below 1.5.
    ex_dupcc measured 1.5 as the exact edge: -WZ 1.4 already costs v510/v1030, -WZ 1.1 costs d510.
    FRAGILITY: ASYMMETRIC. Tightening (lower -WZ) falls off a cliff; loosening (higher -WZ) only
      gives back dup smoothly (-WZ 1.7 leaves the transition untouched). Safe direction available.

#4  -EXR 2.0 / -EXW 0.25                            [plateau, with a cliff beyond]
    PHYSICS: split xy/rz acceptance windows -- r-phi is measured to ~100 um while a 2S strip is
      centimetres in z, so one combined window is forced to the worse coordinate.

    I measured the far side: -EXR 3.5 FAILS v1030 (877) and d15 (523). Cliff is between 2.0 and 3.5.

#5  -WE 0.20, -FBC 0, -EXS 1, -EX 1                 [ROBUST -- discrete or binary, not thresholds]
    -WE is NOT a continuous threshold: with -H 1 the braid denominator is the owner's hit count,
      so every value in (0.167, 0.20] is EXACTLY -WE 0.20. It sits mid-plateau, width 0.033.
    -FBC 0, -EXS 1, -EX 1 are binary/enumerated. There is no cliff to sit near.
    -EXS 1 in particular replaces a hand-made window with the detector's own LS compatibility
      statement, and SKEPTIC-3 showed it delivers 12x the volume at HALF the break rate of the
      tightest free-space window -- it is the most physically-motivated item in the line.

12. WHAT P2 CHARACTERIZATION MUST STILL ABSORB (critic item 10) -- NOT DONE, ENUMERATED
------------------------------------------------------------------------------------------------
The port map is sized against the flagship. The frozen line adds surface it does not describe:
 (a) Extend.cc/.h is an ENTIRELY NEW translation unit and a new stage between K9 and K10, with
     its own claimed-hit bitmap (1 char per ph2 hit row), its own MD/LS lookups and a per-chain
     refit. It needs a row in the section-1 stage table and a line in the section-2.7 memory
     table. It is SEQUENTIAL BY CONSTRUCTION: chains are processed in K9 best-first order and
     each marks its hits claimed so a later chain cannot take them. That places it in the same
     R3 risk class as the K9 greedy walk and it needs the same propose-verify divergence
     measurement. Multiplicity to size against: 18,637 extensions per 300 events = 62/evt,
     12,363-23,966 candidate tests/evt depending on -EXR, 2.03 ms/evt.
 (b) ex_dupcc changes ArbitrationParams (4 new fields) and the K9 claim inner loop (per-candidate
     braid fraction from a band mask + claimOkV). This bears directly on the K9b atomic design.
     The band mask is one char per chain, built from the innermost member T3's |eta|.
 (c) The frozen line's -a 6.875 changes the attach operating point: 144,585 -> more attaches/evt,
     which changes the pair-scoring volume the port map budgets.
 (d) Section-7 item 6 of the plan (record the frozen flag line + the four shipping header md5s in
     the milestone log) is satisfied by sections 1 and 3 of THIS document, but has not been
     committed to git (see section 5).
KNOWN LATENT ITEMS FROM THE CODE AUDIT, carried forward (all inert in the frozen line):
  * Extend.cc:376 vs :425 -- the refit-chi2 gate builds its MD list in STORED order while the
    final CSR rebuild emits it REVERSED, and chainFitChi2Combined's rz term is order-dependent.
    INERT at -EX 1 -EXN 1 (addIn is always empty, at most one MD appended) and inner-end
    extension is already a measured NO-GO. MUST BE FIXED before anyone revisits -EX 2/3.
  * Neither code lever is wired into k9ArbitrateTwoPass (the -A 2 path). CTL is -A 4 so this is
    unreachable in every M19 run, but -A 2 would silently ignore -WE/-FB/-FBC and would leave the
    extension's claimed-hit map without source (a).
  * ex_dupcc's per-band claim tolerance reads params.* while the base reads pp.*, so a band
    candidate would not receive an -FS share-pass loosening. No -FS anywhere in M19; re-check if
    -FS is ever composed with -WE/-FB.
  * The nine -WE/-WZ/-WN/-FB/-FBC/-XP3*/-XT3 and eleven -EX* flags have no usage() help-text
    entry (documented in code comments only). Cosmetic; matters at merge time.
