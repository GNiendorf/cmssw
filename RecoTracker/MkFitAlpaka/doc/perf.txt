      removed the scatter and fused scan + fill (KernelEngineBuildList, one 1024-thread block since 9b2b568:

   6. K3a/K5/K3b/Gather/bkfit: 1.0 ms together; not worth work before 1-3.

2. NUMERICS: propagateHelixToR/Z NO LONGER DEPEND ON INLINING (verify3_int 4a)
  Problem: select's serial stock check dropped from 100% to 92.6% bit-exact propagated parameters when integ forced
  isFinite inline. GCC contracts a*b+c into FMA (-ffp-contract=fast, default in CMSSW) on the inlined, CSE'd
  dataflow, so the result of the R/Z propagators depended on the caller's inlining context.
  Fix (commit 7ff63d5, prop): on host compilers the R and Z propagators are compiled out of line with
  __attribute__((noipa)) (device compilers keep forced inlining; macro MKFITDEV_PROP_HOST_OUTLINE). Stock compiles them
  as exported functions of their own .cc, so this is also the stock structure. Explicit std::fma was considered and not
  used: GCC has no per-expression contraction control, so pinning the FMAs would also need every other a*b+c blocked
  in every caller; an out-of-line body gives the same machine code in every TU.
  This alone fixes the context dependence but not select's N = 1 instantiation: compiled standalone, the N = 1 scalar
  code contracts differently from stock's Matriplex<8> code (select check: par bit-exact 91.6%, err 51%, but max
  pull 1e-3 instead of 0.5). The N = 8 instantiation is bit-identical to stock (prop test). So the K2 propagation
  runs at N = kNN = 8 on CPU (patch 0001 for build, section 4), and both hold:
    prop test (serial, ttbar + QCD captures): all 7 output hashes unchanged, R and Z max diff 0 vs stock;
    select stock check (serial, 20 ttbar): propagated par AND err bit-exact 428573/428573 (main: 396692 / 390631),
      bins 0 mismatches (main: 1), q_c/dq/dphi bit-exact 100%, hit lists 182904/182904 identical;
    CUDA: unchanged (select check identical to verify3_int; device code is not touched).

                                         ttbar chain / stock   ratio      QCD chain / stock   ratio
    b1  main 6f294d1                      70.46 / 55.11        1.279
    b1  repeat                            69.97 / 55.64        1.258      (see REPORT)
    b3  + K3a/K5 at N = kNN               71.92 / 56.22        1.279      no gain
    b5  + K3a/K5 seed loop (+K2 kNN)      64.06 / 56.03        1.143
    b6  final patches                     63.60 / 56.58        1.124      75.69 / 69.39       1.091
  Why N = kNN alone gives nothing: the plane propagation and Kalman bodies are per-slot loops with branches and
  libm calls; without -Ofast they do not vectorize, so N = 8 is 8 scalar slots in a row. Per operation the port is
  already as fast as stock -Ofast (prop test, serial, ns/slot port N = 8 / stock: chi2 220/244, update 278/283,
  plane 211/231, propR 208/146, propZ 97/100).
  What the profile shows instead (perf annotate of K3a): ~45% of K3a's serial time was the loop over the fixed
  (seed, cand, hit) grid (nSeeds x 5 x 6 slots per step, 46 steps), i.e. the integer index decode and the activeMask /
  sel.n loads of mostly inactive slots. On CPU the kernels now walk the seeds (one mask read per seed) and run kNN
  rows per Matriplex. K3a serial: ~18 -> ~8.5 ms/event.
  Patches (against r4/build 1a327a3; the GPU code paths are textually unchanged):
    0001-select-K2-cpu-propagation-kNN.patch      K2 step 1 (R/Z propagation) on 8 candidates per Matriplex on CPU,

                                                   before. Needs prop commit 7ff63d5 for the stock bit-exactness.
    0002-engine-K3a-K5-cpu-seed-loop-kNN.patch    K3a/K5 on CPU: seed loop + kNN batches (runBatch<N>,
