1. BUILD LAYOUT RULE (D-layout; review C2; verify_int 4.1)  -- binding for every lane
  - scram compiles ONLY the top level of src/alpaka/ (*.dev.cc for device code, *.cc for per-backend host code).
    A .dev.cc in src/alpaka/<subdir>/ is silently NOT built. <flags ADD_SUBDIR="1"/> does not help.
  - One top-level translation unit per component: src/alpaka/<Component>.dev.cc. It includes that component's
    kernel headers (src/alpaka/<component>/*.h) and is the ONLY place where those kernels are launched
    (alpaka::exec / createTaskKernel). Today:
        src/alpaka/Cands.dev.cc        cands kernels   -> interface/cands/alpaka/CandSelect.h, CandSeedOpsLaunch.h
        src/alpaka/Clean.dev.cc        clean kernels   -> src/alpaka/clean/CleanAlgo.h (class declaration only)
        src/alpaka/EventOfHits.dev.cc  hits kernels    -> interface/hits/alpaka/EventOfHitsBuild.h
    New components follow the same pattern (round-3 ownership: Seeds*.dev.cc, Select*.dev.cc, Cands*.dev.cc,
    Prop*.dev.cc / BkFit*.dev.cc, Fit*.dev.cc).
  - Exported entry points are plain (non-inline, non-template) host functions or class members in
    ALPAKA_ACCELERATOR_NAMESPACE::mkfitdev[::<component>], declared in a header (interface/<component>/alpaka/*.h or
    src/alpaka/<component>/<Name>.h) and DEFINED in the component .dev.cc. They are real symbols of
    libRecoTrackerMkFitAlpaka{SerialSync,CudaAsync,ROCmAsync}.so.
  - Tests, plugins and other components call the exported entry points. They NEVER launch a kernel class that the
    library also launches: two instantiations of the same RDC kernel in the library and in a test break the CUDA
    device link (nvlink "Internal error: unexpected reloc", seen in round 1). Including a kernel header for its
    constants or device helpers is fine; launching its kernels is not. Test-only kernels (defined in the test) are fine.
  - Device FUNCTIONS (ALPAKA_FN_ACC inline, templates) may be included anywhere; only kernels (alpaka::exec'd
    classes) are subject to the one-TU rule.
  - EventSetup typelookups (TYPELOOKUP_ALPAKA_TEMPLATED_DATA_REG for ESDeviceProduct<ESData<Device>>) live in the
    PORTABLE PLUGIN library (plugins/alpaka/esTypelookup.cc), where every ES producer/consumer lives. Reason: once
    the ROCm core library holds device code, its typelookup symbols were not exported any more (verify_int 4.1 b).
    The host typelookup (ESData<DevHost>) stays in the host core library (src/esTypelookup.cc, no device code).
    If an ES consumer is ever needed outside plugins/alpaka, move the typelookups into a separate package without
    device code (the RecoTracker/LST vs LSTCore pattern) instead of back into the core library.
  - Placeholders: a directory that has a real source does not need its Placeholder file.
  - BuildFiles: integ owns their structure; lanes append <use> lines / <bin> entries only.
  - After removing or moving a source, scram may keep stale objects: run 'scram b clean' for the package.
  - After ADDING files (new .dev.cc, classes_def.xml), scram may not notice: touch the package BuildFile.xml.

2. EVENT PRODUCTS AND DICTIONARIES (C1 f)
  All products are PortableCollections, so the framework copies a device product to the host automatically for a
  host consumer (generic CopyToHost of PortableCollection), and on host backends the device type IS the host type.
  Multi-table products use SoABlocks (GENERATE_SOA_BLOCKS), as LSTCore does: one product, one token, per-block sizes.
  A block view has exactly the type of the standalone layout view, so existing kernels take product.view().<block>().

11. ROOT CAUSE OF THE PLUGIN-KERNEL LAUNCH FAILURE (review M1 a/c; time box used: about 10 min, 2:58-3:08 pm)
  Mechanism (CUDA relocatable device code + one device link per library):
  - The portable plugin library <use>s the core library, so scram device-links the core's static device archive
    into the plugin. The plugin's linked fatbin therefore holds the core kernels too (harness' observation c) and its
    link stub counts NUM_PRELINKED_OBJECTS = 7 core TUs + 2 own TUs = 9 (nm -D: the plugin exports the 7 core
    __cudaRegisterLinkedBinary_<module> symbols plus its own 2; stock RecoTracker/LST plugins export 0).
  - nvcc's crt/link.stub registers a linked fatbin only when ALL its prelinked modules have called
    __cudaRegisterLinkedBinary_<module> (static counter, link.stub:138-157); each TU calls the symbol of its own
    module from its static initializer, resolved by the dynamic linker.
  - Normal job (products test, LD_DEBUG=bindings, main area): the plugin is dlopen'ed first, the core library comes
    in as its dependency, and the core TUs' 7 calls BIND TO THE PLUGIN's copies ("binding file
    libRecoTrackerMkFitAlpakaCudaAsync.so to pluginRecoTrackerMkFitAlpakaPluginsPortableCudaAsync.so ... 7x").
    The plugin's count reaches 9, its fatbin is registered, and core kernels run from the plugin's copy. The core
    library's own linked fatbin is never registered in that job. It works by accident of load order.
  - With the CUDA dictionary inside the core library, ROOT autoloads the core library (rootmap) BEFORE the plugin
    library. Its TUs then bind to the core's own stubs, the core fatbin registers (core kernels work), and the
    plugin's counter later stops at 2/9: the plugin fatbin is never registered, so every plugin kernel launch fails
    (cudaErrorInvalidResourceHandle). That is exactly the bisected symptom.
  Consequences: the same failure returns whenever anything loads the core CUDA library before the plugin (another
  plugin package with its own kernels that uses this library, a dictionary, a test library). Note that
  libRecoTrackerMkFitAlpakaFormatsCudaAsync.so itself has the core CUDA library as a NEEDED dependency (readelf), so a
  ROOT autoload of the Formats dictionary before the portable plugin is loaded would reproduce the failure; today
  the device types are first looked up from produces() inside the plugin's own modules, i.e. after the plugin load. Fix: rule 8c (no
  kernels in plugins/alpaka: no plugin device link, no duplicate registration), as RecoTracker/LST does.
  Evidence files: $L/r4_integ/m1/ (products_cuda.log; the LD_DEBUG binding lines are quoted above).
  Canary: runtests testMkFitAlpakaCudaCanary (test/integ_cuda_canary.sh): the products test on serial (control) and
  on CUDA; a plugin kernel writes known values, MkFitAlpakaProductsCheck throws on any mismatch.

14. SHARED ADAPTERS AFTER H5
  - Loaders: src/alpaka/Packers.h is the implementation of state/track/hit/module-plane copy-in/out, in two input
    forms (HitSoAConstView + ESView; EngineHitInputs) plus hitRow(). Engine (K3a/K3b/K5) and bkfit call it; the
    engine keeps thin N = 1 forwarding names (engineHitRow, loadCandState, loadHit).
    Bit identity (the H5 test): a first version with copyIn from local arrays gave the same stored values but moved
    results at rounding level (engine CUDA step test: states bitwise 97.95% -> 98.03%; serial final fit summaries),
    i.e. it changed the codegen (FMA contraction / vectorization) of the inlined Kalman code, the same effect as the
    isFinite inlining in round 3. Bisected (b5): reverting only the call sites restored bit identity. Packers now
    stores element by element in the lanes' former order; engine + bkfit are then bit-identical on serial and CUDA.
    The final fit (N = 8 on CPU) still moved with that form, so FitKernels.h keeps its inline loader (same stores as
    Packers' HitSoA form, marked in the code). The real fix is prop's (explicit fma where stock contracts, review
    verify3_int 4a), after which the fit can take Packers too.
  - Flags: src/alpaka/PropagationFlagsAdapter.h is the only ES -> prop::PropagationFlags conversion
    (makePropagationFlags, propagationFlags(ESView, stage), propagationFlags(ESConfig, MaterialView, stage)).
    EnginePropConfig carries the ES PropFlags (interface types) and Cands.dev.cc converts; select's
    interLayerFlags forwards; bkfit's local backwardFitFlags and enginePFBits are gone. The final fit keeps stock's
    hard-coded PF_use_param_b_field | PF_apply_material (MkBuilder.cc:1440 does the same).
  - find_tracks_handle_missed_layers: ONE implementation, the engine's (K3b/K4 from SelHits.wsrRaw). Select's
    handleMissedLayer runs only with diagnostics on (diag != nullptr: the select stock check), else extra = 0 and
    wsr = wsrRaw.
