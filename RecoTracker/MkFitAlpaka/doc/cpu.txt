1. COMPILER FLAGS OF THE CPU BACKENDS (decision D5-a)
  Final mechanism (BuildFile.xml of the library, and the testMkFitAlpakaProp bin, which instantiates the prop kernels):
    <flags USE_ALPAKA_SERIAL="ofast-flag&#9;"/>  <flags USE_ALPAKA_TBB="ofast-flag&#9;"/>
    <flags CXXFLAGS="-fopenmp-simd -fno-associative-math -fno-finite-math-only -fsigned-zeros"/>
    <flags REM_ROCM_HOST_CXXFLAGS="(the same four)"/>
  - USE_ALPAKA_<BACKEND> (SCRAM BuildRules.py alpaka_extra_flags) adds a tool to ONE backend product. ofast-flag is
    stock MkFitCore's tool (-Ofast -fno-reciprocal-math -mrecip=none). Checked on the live compile/link lines: the
    SerialSync objects get -Ofast -mrecip=none, the hipcc lines get neither -Ofast nor the CXXFLAGS above.
  - Plain CXXFLAGS reach hipcc (Makefile.rocm AdjustRocmHostFlags) and the nvcc host pass, so -Ofast never goes there.
    The four CXXFLAGS are the defaults of a non-fast-math compile (no-ops there); REM keeps hipcc's line unchanged.
    GCC: an explicit -fno-<x> wins over -Ofast whatever the order (checked with -Q --help=optimizers).
  - CUDA results unchanged: chain on the L40, ttbar 100 events, main vs the -Ofast build: all 9 summary JSONs
    (4 stages, export, final, candidates, mkfit, status) BYTE-IDENTICAL.
  - SCRAM bug (V3_00_95): the per-backend tool is written as "ofast-flag$(if ...parent library...)" (use_public + use
    concatenated without a separator in dumpBuildFileLOC). The trailing &#9; (ElementTree keeps a character reference)
    puts a tab between them; make splits words on it.
  - -fopenmp-simd changes nothing today: the port writes "GCC ivdep" (MPLEX_SIMD) and the generated .ah files dropped
    stock's "omp simd". Kept for flag parity.

5. THE CPU GAP IS PAGE FAULTS: SERIAL-BACKEND BUFFERS ARE NOT CACHED
  - HeterogeneousCore/AlpakaInterface CachedBufAlloc<DevCpu, QueueCpuBlocking> is a plain alpaka::allocBuf ("non-cached,
    synchronous host-only memory"): on the serial backend every make_device_buffer / PortableCollection is a fresh
    malloc. jemalloc 5.3 serves allocations >= 8 MiB (opt.oversize_threshold) from an arena that purges them on free, so
    every event re-faults its large buffers. The EventOfHits product alone is one 31 MB allocation; the build module
    allocates 41.7 MB per event (FastTimer mem_alloc); stock mkFit allocates per layer / reuses pools (EOH 39.9 MB in
    small vectors, MkFitProducer 12.1 MB).
  - Evidence (replay throughput job, 8 threads, 600-1000 events; INDICATIVE, load 40-95):
      page faults per job (perf stat): inputs only 9.2M, stock 11.6M, port 18.4M; page-fault profile (perf -e
        page-faults): fillHits 14.6% (product hits block), KernelBuildCpu 8.8%, engine GatherSeeds 5.8%, SeedInitCands 5.1%;
      FastTimer thread time = real time (27.3 ms EOH): the gap is sys time, invisible to a user-only perf profile.
      MALLOC_CONF=oversize_threshold:0 (no special arena): port job 45 -> 74 ev/s, EOH 27 -> 14 ms, build 57 -> 47 ms.
  - Experiment (ref0 = main B6 + a local copy of HeterogeneousCore/AlpakaInterface whose CachedBufAlloc for the blocking
    CPU queue uses the host CachingAllocator, as the GPU backends' pinned host memory does; 8 lines,
    L/r6_cpu/patches/cachexp_CachedBufAlloc.diff), default malloc, alternated with main:
                           EventOfHits(dev)   Build(dev)    mem_alloc/event (EOH / build)
      main (no cache)      27.6  31.5         55.9  63.2    45.4 / 41.7 MB
      ref0 (cached)        13.2  14.5         46.2  49.9     0.6 /  0.5 MB
      stock -Ofast (old)   EOH 12.6           MkFitProducer 48.3
    Physics unchanged: the in-job ttbar 200 arm of the cached build equals r0B6 exactly (24+27 / 22+21, status clean).
    (ref0 has the OLD EOH kernels; the new CPU kernel is a further -6% on the EOH compute, section 6.)
  - So with cached CPU buffers the CPU chain (EOH + build) is at stock speed in the replay. The fix is a CMSSW core change
    (or a job-level MALLOC_CONF), outside our packages: coordinator/owner decision. Inside the package the scratch of
    the CPU EOH kernel is now per-thread (reused, no allocation); products cannot be pooled (PortableCollection has no
    constructor from a buffer).

6. CPU EVENTOFHITS KERNEL (src/alpaka/hits/EventOfHitsKernels.h, CPU backends only)
  KernelBuildCpu: one sequential kernel (1 block x 1 thread; the serial backend runs one event per thread anyway):
    a) hits per layer -> hitBegin/nHits (layers concatenated in layer order);
    b) registerHit in chunks of 16: a branch-free loop computes info + (fine phi << 24 | bin in layer) (binHit, shared
       with the GPU KernelBinHits: one copy of the arithmetic), a scalar loop appends to the hit's layer (increasing
       original index = stock registration order);
    c) per layer, in cache: bin histogram + fine-phi histogram; the bin table written once (C_pair, dead = 0, overflow
       counters); stable counting sort by fine phi, then stable scatter by bin = (bin, fine phi, index) = stock's LSD
       radix order; outputs written at their final row.
  No sort, deterministic, no atomics. Scratch: per thread on the serial backend (thread_local, grows to the largest
  event: ~28 B/hit + 256 KB); TBB (not built) uses queue-ordered device buffers.
  Validation: testMkFitAlpakaHits{SerialSync,CudaAsync} on hits_dump_ttbar (10 ev) and hits_dump_ttbar_dead (20 ev,
  313,743 dead bins): order, bin table, hit infos, dead bins bit-identical to stock (non-Ofast dump); lowocc40: the
  documented 16 std::sort-path ties, as before. GPU path unchanged (KernelBinHits calls the shared binHit; bit-identical;
  registers sm_89 48 -> 58, sm_80/100/120 64, LOCAL 0 everywhere).
  Speed: single thread (replay test, quiet moment) 10.3 vs 12.5 ms/event; replay 8 threads with page faults removed
  (oversize_threshold:0), normalised by the stock hit converters: EOH/conv 1.97 (old kernels) -> 1.85 (new), stock 1.66.
  In the default configuration the module time is page faults (section 5), so the kernel alone does not move it.

9. PER-STREAM SCRATCH (D7-c: inside the package, no core change)
  What a CPU event allocates (ttbar PU200, 1.5-4k seeds, ~430k hits), and what jemalloc does with it (>= 8 MiB =
  oversize arena, purged on free -> re-faulted every event):
    build module scratch (EngineBuffers x2: seeds/slots/hots/opts/extras/upds/sel/c2; K2 list/props/sels)  ~42 MB/ev
    EventOfHits device-hit raw host rows (DeviceHitRawSoA, 32 B/hit)                                       ~14 MB/ev
    EventOfHits PRODUCT (one PortableCollection over hits/layers/binnedHits/bins)                           ~31 MB/ev
    fit scratch (key/chi2f/chi2b/order per track x kMaxTrkHits; CPE cluster rows)        each buffer < 8 MiB: kept
    seeds/clean/export TrackSoAs                                                          KB to a few MB: kept
  Change (15def62):
  - MkFitAlpakaBuildProducer = global::EDProducer<edm::StreamCache<BuildScratch>>. BuildScratch holds both EngineBuffers
    and the K2 collections at a grow-only seed capacity (n + 25%, rounded to 1024 seeds); on reuse the seed rows are
    zeroed and nRowsDev reset, exactly the state the EngineBuffers constructor leaves. Everything the engine runs is
    bounded by the seed count n passed in and the device row counts; rows past n are initialised as unused by the
    import kernel (it already loops over the capacity) and never read. scratchReuse: 0 = per event, 1 = CPU backends
    (default), 2 = every backend.
  - MkFitAlpakaEventOfHitsProducer (deviceHits): on CPU backends the DeviceHitRaw host rows are a per-stream
    collection (grow-only, +25%); fillRaw takes the row count explicitly (it used the collection size). GPU backends
    keep the per-event pinned host buffer (already cached by the CMSSW host allocator).
  - Safety: an EDM stream starts its next event only after the device work of the current one has completed (the
    products' EDMetadata synchronises in its destructor), so a stream's scratch is never in use by two events.
  - Not possible in the package: the EventOfHits PRODUCT (PortableCollection has no constructor from a buffer, and an
    event product cannot be recycled by its producer). It is the largest remaining fault source on CPU (31 MB/event).
  Results (target menu, --procModifiers trackingMkFitFit + customizeHLTforMkFitAlpakaTarget, 8 threads, CPU serial):
  - Byte identity (scripts in L/r7_cpu/scripts: cmp_tracks.py = md5 of every track's parameters, covariance, chi2,
    ndof, reference point, momentum, hit-pattern counts, algo, quality per event and collection; main6 = before):
      ttbar 200 events (139 tracked): hltInitialStepTracks, ...TorchClassifierOutput, ...SelectionHighPurity,
        hltGeneralTracks, hltSeedsForMkFit, hltPhase2PixelTracks: IDENTICAL in 200/200 events. (Only the legacy L3-muon
        CKF collections differ in 36 events: their PixelTrackProducer input differs too, i.e. run-to-run, not ours.)
      QCD 100 events: all 12 compared collections IDENTICAL.
  - Allocation: BUILD_MEM scratch per stream 63.8 MB mean / 81.7 MB max (capacity incl. headroom), 9 allocations in
    139 events on 8 streams (8 first + 1 regrowth); QCD 68.5 / 82.4 MB, 8 allocations. Job page faults (time -v):
    30.6M -> 28.7M (ttbar 200, whole job incl. startup). Job max RSS 9.74 -> 10.04 GB (+0.3 GB at 8 streams: the
    scratch now stays resident between events, ~80 MB per stream).
  - GPU: scratchReuse = 2 raises the per-job device memory peak from 2128 to 2872 MiB (8 streams, ttbar 200, L4):

11. R6-M3: C++ guard of the device-hit input (plugins/alpaka/MkFitAlpakaEventOfHitsProducer.cc, fillRaw)
  A pixel row found through the cluster's originalId (moduleStart + originalId) is accepted only if the SoA local
  position is bitwise the legacy rechit's (the legacy one is a copy of the SoA one); otherwise, and for clusters without
  originalId, the row is found by position (the existing search, which still throws if nothing matches). Both cases
  are counted: LogWarning on the first event with any, DEVICE_HITS_GUARD totals at endJob; a key mismatch throws under
  compareHostHits. Menu runs: keyMismatch 0, positionSearch 0 (ttbar 200, QCD 100). With this, DEVICE_HITS (already
  True in the target customise) is backed by the C++ check D7-d asked for.

12. R6-M5: per-IOV CPE cross-check of both fit producers (MkFitAlpakaFitDeviceProducer, MkFitAlpakaFitProducer)
  The checked record ids are atomics with a lock-free fast path (no mutex per event); under the mutex the check runs and
  the ids are stored only AFTER it has passed (or warned). With a failing check under cpeCheck = 'throw' every stream
  now checks and throws (before: the first stream stored the ids and threw; the others skipped the check).
